# Operations automation case study

> Обезличенный публичный кейс по автоматизации внутренних процессов строительной компании. Основан на реальном проектном опыте; названия систем, идентификаторы, персональные данные и внутренние показатели исключены.

## Задача

На старте процессы жили в чатах, таблицах и личных договорённостях. Не было единого маршрута заявок, прозрачных статусов, закреплённых ролей, общего backlog и проверяемых правил уведомлений.

Целью было выстроить операционный контур: от формализации процессов и требований до конфигурации трекера, автоматизации уведомлений и тестового запуска.

## Моя роль и вклад

- описал AS-IS / TO-BE, роли, статусы, маршруты и бизнес-правила;
- подготовил USER STORY и критерии приёмки для участников процесса;
- участвовал в настройке очередей, локальных полей, досок и триггеров в трекере задач;
- **самостоятельно разработал на Python сервис интеграции и автоматизации**: обработка webhook-событий, создание связанных задач, синхронизация данных, уведомления и защита от дублей;
- организовал тестовый контур, проверял сквозные сценарии и участвовал в rollout в рабочий контур;
- подготовил регламенты и структуру базы знаний.

## Снабжение — один из реализованных сценариев

Сценарий закупки материалов иллюстрирует общий подход, а не ограничивает проект только снабжением:

```mermaid
flowchart LR
    A[Инициатор создаёт заявку] --> B[Снабжение уточняет и формирует счёт]
    B --> C[Финансы согласуют оплату]
    C --> D[Бухгалтерия проводит оплату]
    D --> E[Контроль поставки и документы]
    B -. webhook .-> F[Python-сервис автоматизации]
    F -. создаёт связанные задачи и уведомления .-> C
    F -.> D
```

## Запуск примера

```bash
python -m unittest discover -s tests -v
```

В примере нет токенов, URL, идентификаторов сотрудников, названий внутренних очередей или кода, скопированного из рабочего контура. Это самостоятельная портфельная реализация на синтетических данных, демонстрирующая применённые инженерные принципы.
